Show the app as a map, not only as a ledger

What project-visualisation tools on other platforms do on their first screen, what recurs across them, and the three additions RailsVis can derive from code without a new runtime dependency.

Where we can improve

The first screen counts things; it does not yet show how they connect. No view answers “which page leads where”.

What to expect

A page-flow view, a start screen that reads as a map, and an inventory of templates and view components, each row still a source line.

Why it fits Rails

Named routes are the link language of every template and redirect. Reflection plus one Prism pass yields the graph; nothing is hand-maintained.

Use the arrow keys or the buttons above. Every figure in this deck comes from the repository or the Spina acceptance dump; links go to the sources.

    What recurs elsewhere: eight patterns, each with the tool that proves it

    About 45 tools read from their own docs and manifests. The full list with a URL per claim is in the source notes beside this deck.

    Entry point first

    Sourcetrail centres the graph on the selected symbol and shows only its in and out edges. Nx focuses one project. Android’s Navigation Editor is organised around a start destination.

    Counts that are links

    pkg.go.dev’s “known importing packages”, Laravel Pulse’s queue card, Sourcetrail’s member counts. RailsVis already does this on Start here.

    Colour means kind, never decoration

    Sourcetrail by symbol kind, Madge by dependency state, Swagger UI’s method badges. RailsVis already has the four review roles and the verb pills.

    Click a node, land on code

    Sourcetrail, Nx (“click any dependency line to find which file created it”), dependency-cruiser, NDepend, Mermaid’s click binding. Our rows do this; our diagram nodes do not yet.

    Focus with a depth control

    Sourcetrail’s depth slider, Nx proximity, code2flow upstream and downstream depth, Backstage maxDepth, Azimutt find-path.

    Collapse by folder or namespace

    The universal scaling trick: dependency-cruiser archi, Nx group by folder, rails-erd cluster, Mermaid subgraphs that collapse to one node.

    Hover highlights, click pins

    dependency-cruiser’s dot-webpage and NDepend do this on a static SVG. It gives most of the felt interactivity of a graph library without one.

    The page-flow convention

    Screens as nodes, actions as labelled arrows, the start marked, a nested flow drawn as one node: Android, Xcode segues, FigJam and Miro user-flow templates.

    Why 22 orphans, and the fix

    Spina’s admin navigation lives in a layout partial (10 helper calls) and in Ruby view components (10 files). The spike attributes neither to a page. The collector would treat layout links as a global-nav hub and scan app/components with the same pass.

    What is derived, what is deferred

    • Derived: verb, path, template, filters, models, redirect target, jobs and mailers the action names
    • Deferred: string-built paths, Turbo or JavaScript navigation, Inertia client links (a TSX scan later)
    • A sentence about what a page does is authored, never derived

    Dependencies needed: none. action_view and prism are already in the bundle. Plain Erubi was not enough: it emits invalid Ruby for <%= link_to … do %>, which is why the first spike found nothing.

    Page flow, live: the Spina admin as a node graph from real templates

    Drag a page. Click one to light its neighbours. Double-click to open the template at the commit. Dashed pages have no inbound link in a template.

    No library: an inline spring layout in about 30 lines of script. A layered layout (dagre or ELK) would rank pages left to right; that is the one thing this sketch does not show.

    Recommended: Mermaid plus post-processing

    Mermaid 12 already bundles ELK, so a layered left-to-right flow is paid for. Add click bindings to templates, subgraphs per controller namespace that collapse, and hover-highlight with click-to-pin on the SVG the viewer already wraps. One visual language for both diagrams.

    What it cannot do

    Drag nodes by hand. If that turns out to matter after use, Cytoscape.js with cytoscape-dagre is the stack Nx ships for a static page, at 8% of today’s payload. d3-force is cheaper but draws a cloud, the wrong shape for a flow.

    Ruled out

    React Flow needs React. GoJS is commercial. JointJS keeps its layouts in the paid tier. vis-network, G6, Sigma.js and ELK.js alone cost more than a megabyte each for nothing Mermaid lacks.

    The live demo two slides back is the own-layout sketch, there so the idea can be judged by handling it; it is not the proposed implementation.

    Start here as a map: lead with where the app is entered, then with what is busiest

    Entry points first

    One row per way in, each with a count and a link: the root route and its page, the sign-in page when one exists, jobs and their queue, recurring tasks, mailers, channels. All of it is already collected.

    The busiest paths

    Keep the routes-per-controller bars, and add the three pages with the most outbound links from Proposal B. “Busiest” means most connected, not most visited: nothing is measured at runtime.

    A thumbnail of each map

    Small static versions of the page flow and the domain diagram that open the full view. The first screen then says “this is the shape” before it says “here are the counts”.

    Nothing on this screen is invented: every tile is a count of rows that exist in data.json, and every tile links to those rows.

    Prerequisite defect: the controllers collector globs app/views under the app root, so an engine like Spina resolves 0 of 391 views. Resolving through the controller’s view paths is the reflect-not-parse rule applied to views, and page flow depends on it.

    Expected outcome: three more questions a newcomer answers from the dashboard alone

    “How do I get to that screen?”

    Page flow: pick the page, read its inbound links, follow them back to the entry page. Today this takes a grep for the route helper.

    “What happens after I submit?”

    The write action’s redirect landing is an edge in the same graph, so the create-then-show loop is visible without opening the controller.

    “Where does this partial get used?”

    The inventory lists renderers per partial and per component, which is the first thing a reviewer checks before changing one.

    What stays true

    • One static HTML file, no server, no network at view time
    • Every node is still a file and line at a commit
    • Failing nodes become warnings, never an abort

    What it costs

    • One collector (pages and links) and one view
    • A template-resolution fix that engines need anyway
    • If a node-graph library is adopted: its size, decided on the next slide’s numbers

    Why it suits Rails review: convention makes the graph cheap, and reflection makes it honest

    Named routes are the link language

    Every link_to, form_with, button_to and redirect_to in idiomatic Rails names a route helper. The route name is already in data.json, so one Prism pass over compiled templates resolves most edges with no heuristics.

    The app is booted, not guessed

    Routes, view paths, engines and components come from the live application, so engine views, custom inflections and mounted routes resolve the way Rails resolves them.

    Reviews start from flow

    A Rails review of a feature reads the route, the action, the redirect and the template in that order. The page-flow view is that reading order drawn once, for the whole app.

    Where other stacks need a build step or a runtime tracer for this picture, Rails gives it from conventions plus the booted app, which is what RailsVis already does for routes and models.

    To decide: four calls that are yours

    1. Order. B (page flow) first, then the view-path fix it needs, then A and C? Or A first because it changes the first screen?
    2. Node graph engine. Keep Mermaid for both diagrams, or add a small graph library for the page flow so nodes can be dragged and focused. The sizes are on the node-graph slide, and the recommendation is to stay on Mermaid.
    3. Scope of links. Templates and partials only, or also view components and layouts in the first cut.
    4. Inertia. Defer the TSX link scan, or include a minimal <Link href> pass now so Inertia apps are not blank in the flow.
